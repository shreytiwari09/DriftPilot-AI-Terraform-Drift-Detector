# Real-AWS demo (prepared, not applied)

This folder builds a **small, real, cheap** piece of AWS so DriftPilot can be shown on the real thing, not only on mocks.
**Nothing here has been applied.** It was written and checked offline (`terraform validate`, tests with an AWS mock). The first
time anything real happens is when *you* run `scripts/aws_demo.sh apply` and type the region name to confirm.

> **Money warning.** Your AWS credits pay for this, and the database bills **every hour it exists**, used or not.
> Run the demo, then **destroy it straight after** (`scripts/aws_demo.sh destroy`). The cost figures below are **my estimates**.
> Check them yourself on the AWS pricing pages and in the console (Billing and Cost Management, then Credits) before you start.

## What it creates

| Resource | Why | Settings that matter |
| --- | --- | --- |
| S3 bucket `driftpilot-demo-<random>` | something for scenarios 20 and 24 to change | all four public-access-block flags on, versioning on, SSE-S3 encryption, `force_destroy` so `destroy` empties it |
| Security group `driftpilot-demo-db` | scenario 21 | port 5432 only from **your** IP (a `/32`). `0.0.0.0/0` is rejected by a validation rule |
| RDS PostgreSQL 16 `driftpilot-demo-db` | scenarios 22 and 23, and the database-drift demo | `db.t4g.micro`, 20 GB gp3, single-AZ, encrypted, `publicly_accessible = true` (so your laptop can connect; the security group limits who), backups kept 1 day, no final snapshot, no deletion protection, no Performance Insights, no enhanced monitoring |
| random password | the database login | generated by Terraform, hidden in output, stored in local state |
| AWS Budgets alert (optional, off by default) | warns you by email at 80 % of US$20 | `enable_budget_guard = true` plus your email in `terraform.tfvars` |

Every resource is tagged `demo=driftpilot` and `team=platform`. The helper script and the drift injector only act on things with that tag.

**Not created on purpose** (each can cost money by itself): NAT gateway, load balancer, EC2 instances, Elastic IPs, Secrets Manager,
CloudTrail trails (the free 90-day Event history is always on), Multi-AZ, read replicas, Performance Insights.

## Before you start (once)

1. **Install the tools** (macOS, Homebrew): `brew install awscli`, and for the database demo `brew install libpq` (gives you `psql`;
   then `brew link --force libpq`) and Docker Desktop. Terraform is already installed.
2. **Never use your root login for this.** Create two small users in the console (click-by-click below). *IAM* is AWS's
   permission system: a *user* is a login for a program, a *policy* is a list of things it may do.
3. **Create the two policies.** AWS console, search **IAM**, then **Policies**, **Create policy**, tab **JSON**. Delete the example,
   paste the whole content of `iam-policy-demo-operator.json`, **Next**, name it `DriftPilotDemoOperator`, **Create policy**.
   Repeat with `iam-policy-driftpilot-readonly.json` and the name `DriftPilotReadOnly`.
   (They must be *customer managed policies*: an inline policy is limited to 2,048 characters and the operator one is longer.)
4. **Create the users.** IAM, **Users**, **Create user**. Name `dp-demo-operator`, leave "Provide user access to the AWS Management Console"
   **unticked**, **Next**, **Attach policies directly**, tick `DriftPilotDemoOperator`, **Create user**. Do the same for
   `dp-demo-readonly` with `DriftPilotReadOnly`.
   (Keep the names starting with `dp-demo-`: the scanner's settings in `.driftpilot.yml` skip those, so these users are not reported as "unmanaged".)
5. **Create an access key for each user.** Open the user, tab **Security credentials**, **Create access key**, choose
   **Command Line Interface (CLI)**, tick the confirmation, **Next**, **Create access key**. The page shows an *access key ID* and a *secret*.
   **Do not paste them in any chat, file, email or screenshot.** Keep the page open for the next step.
6. **Put the keys in a named profile on this laptop** (they go to `~/.aws/credentials`, outside the repo):

   ```bash
   aws configure --profile driftpilot-demo      # paste the operator's key ID and secret when asked; region: ap-south-1; output: json
   aws configure --profile driftpilot-readonly  # the read-only user's keys; region: ap-south-1
   ```

   Then close the browser page. If a key is ever shown anywhere it should not be, delete it (IAM, user, Security credentials, Deactivate, Delete) and make a new one.
7. **Check that the profile works** (this only asks AWS "who am I?"):

   ```bash
   AWS_PROFILE=driftpilot-demo aws sts get-caller-identity
   ```

8. **Find your public IP** and write it in `terraform.tfvars` (this file is gitignored, never commit it):

   ```bash
   curl -s https://checkip.amazonaws.com        # for example 198.51.100.9
   cd demo/aws && cp terraform.tfvars.example terraform.tfvars
   # edit terraform.tfvars: my_ip_cidr = "198.51.100.9/32"   (your address, then /32)
   ```

   If your IP changes later (new Wi-Fi, mobile hotspot), update the file and `apply` again, or you will get connection time-outs.

## Run it (details and exact order: `RUNBOOK.md`)

```bash
export AWS_PROFILE=driftpilot-demo
scripts/aws_demo.sh plan          # shows what would be created; changes nothing
scripts/aws_demo.sh apply         # shows the plan again, then waits until you type ap-south-1
scripts/aws_demo.sh status        # lists the live demo resources
...                               # scan, inject drift, scan again (RUNBOOK.md)
scripts/aws_demo.sh destroy       # shows what will be deleted, waits until you type ap-south-1
scripts/aws_demo.sh check-clean   # exits 1 if anything tagged demo=driftpilot is still there
```

`apply` takes roughly 5 to 10 minutes (my estimate): RDS is slow to start. **Terraform state** is Terraform's notebook of what it
built. Here it lives in `demo/aws/terraform.tfstate`, on this laptop only. **It contains the database password in plain text**,
so it is gitignored (`*.tfstate*`), never put it in a bucket, a chat or a commit. Delete the file after a successful destroy.

## The drift scenarios (20 to 24)

`scripts/inject_drift.py` changes the *real* demo resources by hand, the way a person in a hurry would. It needs
`DRIFTPILOT_AWS_DEMO=1`, a region (`AWS_REGION=ap-south-1`) and your profile, and **refuses any resource that is not tagged `demo=driftpilot`**
(the bucket must also be named `driftpilot-demo-*`). Each scenario has a revert.

| # | What the "person in a hurry" does | DriftPilot should say |
| --- | --- | --- |
| 20 | turns the bucket's S3 public access block off | critical, revert (never softened by the AI) |
| 21 | opens SSH (port 22) to `0.0.0.0/0` on the security group | critical, revert (never softened) |
| 22 | sets database backup retention to 0 days | high, revert |
| 23 | flips `publicly_accessible` (see below) | depends on the direction |
| 24 | adds a harmless tag `reviewed-by=hand` to the bucket | low, codify (keep it, update the code) |

```bash
export DRIFTPILOT_AWS_DEMO=1 AWS_REGION=ap-south-1 AWS_PROFILE=driftpilot-demo
python scripts/inject_drift.py inject 20 21
python scripts/inject_drift.py revert 20 21
```

**Scenario 23, which direction is drift?** The code says `publicly_accessible = true` (so your laptop can connect). The injector sets it
to the *opposite*, `false`. That is real drift (reality differs from the code), but it makes the database *safer*, so the
"made public" rule does not fire and the change goes to the AI or to a person ("someone locked it down: keep it or revert?").
For the dramatic direction (a private database made public, always critical): set `db_publicly_accessible = false` in `terraform.tfvars`,
`apply`, then `export DRIFTPILOT_AWS_DEMO_PUBLIC=false` and inject 23, which turns it **on**. With the database private you cannot connect
from your laptop, so use that only for the infrastructure part of the demo.
RDS changes take a few minutes: wait until `status` shows `available` before scanning.

## Check that nothing is left

`scripts/aws_demo.sh check-clean` does this by command. To see it with your own eyes (always switch the region selector, top right, to
**Asia Pacific (Mumbai) ap-south-1**):

1. **RDS**: *Databases* is empty; *Snapshots* (tabs *Manual*, *System*) empty; *Automated backups* (tabs *Current Region* and *Retained*) empty.
2. **S3**: *General purpose buckets* has no `driftpilot-demo-...` (S3 lists all regions together).
3. **EC2**: *Security Groups* has no `driftpilot-demo-db`; *Snapshots* and *Volumes* are empty; *Elastic IPs* is empty (this demo never creates any).
4. **Billing and Cost Management**: *Bills* and *Credits* for the day after: the daily cost should fall to about zero.
5. If a **budget** was created: *Budgets* shows none named `driftpilot-demo-guard` (it is free, so leaving it costs nothing).

## What the two IAM policies allow, and why

They were derived from what Terraform's resources, the helper script and the drift injector actually call, not copied from
"AdministratorAccess". **They have not been tried against real AWS** (no account was available when they were written). If a step ends
in `AccessDenied`, the error names the missing action: add it in the IAM console (*Policies*, `DriftPilotDemoOperator`, *Edit*) and tell me.

`iam-policy-driftpilot-readonly.json` (for `driftpilot scan`; changes nothing):
- S3: `ListAllMyBuckets`, `GetBucketLocation` (the scanner lists buckets), and read-only `ListBucket`, `GetBucket*`, `GetEncryptionConfiguration`,
  `GetLifecycleConfiguration`, `GetReplicationConfiguration`, `GetAccelerateConfiguration` on `driftpilot-demo-*` buckets only (Terraform's refresh reads these sub-settings).
- EC2 `Describe...` (security groups and their rules, VPCs, subnets, account attributes, availability zones, internet gateways,
  network interfaces, tags, snapshots); RDS `Describe...` and `ListTagsForResource`; `iam:ListUsers` (the scanner lists IAM users);
  `budgets:ViewBudget`; `tag:GetResources` (finds everything tagged `demo=driftpilot`).

`iam-policy-demo-operator.json` = the read-only list, plus:
- S3 create/delete/tag/public-access-block/versioning/encryption, and `ListBucketVersions`, `DeleteObject`, `DeleteObjectVersion` (for `force_destroy`), on `driftpilot-demo-*` only.
- EC2: `CreateSecurityGroup` only when the request is tagged `demo=driftpilot`; authorize/revoke rules, delete group, create/delete tags only on groups that
  **already carry** `demo=driftpilot`.
- RDS: `CreateDBInstance` (+ `AddTagsToResource`) only when tagged `demo=driftpilot`; `ModifyDBInstance`, `DeleteDBInstance`, tag changes only on `driftpilot-demo-*` databases
  that carry the tag.
- `iam:CreateServiceLinkedRole` for `rds.amazonaws.com` only: the very first RDS database in an account makes AWS create a helper role.
- Budgets: modify, tag only budgets named `driftpilot-demo-*`.

Region: EC2, RDS and the tagging call are limited to `ap-south-1` with `aws:RequestedRegion`. S3, IAM and Budgets are global services, so they use names instead.

**Wildcards I had to keep, and why:**
- `Resource: "*"` on the `Describe...`/`List...` calls (EC2, RDS, `ListAllMyBuckets`, `iam:ListUsers`, `tag:GetResources`): AWS does not support resource-level limits on these list calls, and the scanner must see the whole account to find things not in Terraform.
- `s3:GetBucket*` (read-only, only on `driftpilot-demo-*`): Terraform's S3 refresh reads about a dozen separate `GetBucket...` settings; listing each one would add nothing but length.
- `arn:aws:...:*:...` (any account number) in ARNs: a policy only works in the account it is attached to, so this avoids you editing the files.
- `budgets:ViewBudget` on all budgets: listing budgets cannot be limited by name.
- Security-group-rule ARNs (`security-group-rule/*`) have no tag condition: rules carry no tags of their own; the group's tag condition still decides.

## Troubleshooting

- *Timeout connecting to the database*: your IP changed (update `terraform.tfvars`, `apply`), or the instance is still `creating`.
- *No default VPC*: some old accounts deleted theirs. Console, VPC, *Your VPCs*, *Actions*, *Create default VPC*.
- *`DBSubnetGroupDoesNotExistFault`*: same cause; create the default VPC.
- *`AccessDenied` on RDS create the first time*: the service-linked role statement above is missing from your policy.
- *Terraform says the plan file is stale*: run `apply` again; it re-plans every time.
